# v11.4 更新与缺失修复

本版修正升级完成后仍显示“准备任务范围 / 1%”的任务状态，并减少健康状态轮询对媒体表的重复统计。增加完整检查明细及缺失原文件恢复入口。

## NAS 更新

1. 使用已有方式保留 `config` 与 `data`；需要备份时应先停止应用，使两者处于同一时点。沿用原有两个数据目录挂载。
2. 在镜像包所在目录导入：`docker load -i zzs-bili-gallery_v11.4_amd64.tar`。
3. 解压本版部署包。核对 `docker_app/docker-compose.nas-amd64.yml` 的两条挂载路径与当前部署相同，镜像为 `zzs-bili-gallery:11.4-amd64`。
4. 进入 `docker_app` 目录，执行 `docker compose -f docker-compose.nas-amd64.yml up -d`。保留随包 `xhs_worker/seccomp_profile.json` 的相对位置。

镜像包包含完整基础层，不依赖 NAS 上预先存在 v11.3 镜像。本版复用 v11.3 的浏览器与媒体运行环境，不改现有登录配置。

## 处理旧的缺失统计

已经完成布局升级的库不需要重新迁移目录。在“设置 → 维护 → 数据检查”点击“重新检查并修复缺失”。任务期间页面接管，结束后自动恢复访问。

旧检查曾把站点去重后 `status=duplicate` 的历史路径也算作缺失，新检查会显示已排除的数量。旧报告中的 649 条不代表已经确认丢失 649 个原文件，应以重查结果为准。

真正缺失的原文件会尝试找回同一图库内容目录中的原件，或使用已有站点原文件地址补下；已有文件、空文件和多个候选都会保留现场。下载内容经过媒体格式校验后原子创建目标，不覆盖原文件、不删除数据库记录。修复一次后即结束，失败项目不会自动循环重试。

点击“查看检查明细”查看全部项目、已恢复状态及仍未恢复的原因。无地址、地址过期、原站下架以及小红书历史链接等情况需要重新同步对应来源。完整明细保存在 `config/data-check-report.json`。

状态接口 `/api/settings/data-upgrade` 中 `status=completed`、`progress=100`、`blocked=false` 表示本轮维护已结束；残留缺失数量在 `result.missing_assets` 中，不能仅以任务完成判断全部文件可用。

详细结构与测试边界见 [data-layout-upgrade.md](data-layout-upgrade.md)。
