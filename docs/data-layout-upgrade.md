# 数据结构升级与大图库加载

旧库仍可浏览，设置 → 维护 → 数据检查会显示“旧版数据（脏）”。升级由用户点击“升级数据结构并迁移目录”开始，不会在首页后台自动移动媒体。说明文字收纳在 `?` 中。“检查数据”仅检查数据库和原文件引用，不升级布局，也不自动删除缺失记录。

## 数据库布局

SQLite 本身使用分页 B 树。v3 在原有设置库、浏览索引库之外，将内容按来源分成三块；主库保存查找表和公共事务状态：

| 文件 | 内容 |
| --- | --- |
| `config/app.db` | 内容路由、全局 ID 序列、目录映射、任务、审核、回收站等公共状态 |
| `config/control.db` | 设置、登录状态、订阅、侧栏计数缓存 |
| `config/browse.db` | 首页卡片、来源/视频筛选、作者与原链接、页面缓存、分页边界、随机浏览快照 |
| `config/bilibili.db` | B站动态、媒体、Live Photo 持久配对 |
| `config/sites.db` | 站点订阅、贴文、媒体、筛选记录、持久配对 |
| `config/xiaohongshu.db` | 小红书来源、笔记、媒体、同步状态、持久配对 |

发布时间、来源与入库时间有复合索引，入库时间从原 `folders.created_at` 保留。连续分页从边界索引定位；直接跳页无边界时使用偏移查询。v3 正常卡片请求只打开 browse/control，不挂载内容库；作者、原链接和视频数在索引写入时保存，作者/站点信息变化在同一事务内更新卡片。控制库的无关设置变化不使整页缓存失效。索引不完整时也先在 SQL 分页，再批量加载当前页媒体。首页先请求卡片，完成后再初始化统计与订阅；磁盘容量统计仍仅显式刷新或清理任务时扫描。

v3 升级在逐表校验和事务提交后执行主库 `VACUUM`，回收搬走内容所留下的空闲页，并更新查询统计。需要预留临时压缩、分库副本、回滚日志和备份空间。旧 v2 只拆模块而没有压缩主库，因此截图中大 app.db 不能单独用于判断当时是否升级成功。

## 媒体目录

```
data/images/bilibili-<订阅 UID>/<日期>/<原内容目录>/...
data/livephoto/bilibili-<订阅 UID>/<日期>/<原内容目录>/...
data/images/xhs-<来源 ID>/<日期>/<原内容目录>/...
data/livephoto/xhs-<来源 ID>/<日期>/<原内容目录>/...
```

没有来源信息时使用 `bilibili-unknown`。日期无法解析时使用 `unknown-date`。`sites` 保持现有布局。`folder_locations` 保存内容与实际目录的对应关系，新下载与重建索引也使用该表。迁移移动整个内容目录，保留原始媒体、配对标识和文件名；同时更新媒体、浏览索引、回收站与持久 Live Photo 配对中的路径。

数据统计会把媒体 `.thumbs/tiny` 中已废弃的缩略图算入垃圾文件；订阅头像、站点图标及其他仍在使用的文件受到保护。统计后仍需点击清理或启用定期清理才会删除。

升级会清除包含旧媒体地址的重复检测缓存，保留已忽略重复组的选择；可在重复内容页重新检测。历史 Live Photo 检查和手动选图也会按新的目录映射查找原文件。

## 独占、备份和中断恢复

应用保持单容器、单 Uvicorn worker，同一 `storage` 的第二个应用进程会拒绝启动。不要让其他版本容器、外部脚本或数据库编辑器同时写入这份数据。网络文件系统必须提供可靠的 SQLite 文件锁和同文件系统目录重命名语义。

开始后所有客户端进入独占进度页面，API 与媒体请求返回维护状态。已接受的 HTTP 请求（含流式响应与响应后台任务）结束后才迁移；队列、调度器和独立图标任务也必须停止写入。期间不能进入图库或修改设置。

1. 在 `config/backups/<代次>/` 保存一致的升级前快照。SQLite 备份 API 在全部数据库的写入保留锁内复制，完整回读结构、外键、路由与计数后才发布代次；失败文件留在 `.pending-*`，不冒充完整备份。旧 `before-data-layout-v2/` 快照继续保留。
2. 日常写入和迁移统一使用 SQLite DELETE journal + EXTRA synchronous，同一连接上的跨文件事务由 super-journal 提交。每条逻辑分库写入还有 savepoint，捕获错误后继续事务也不会留下半条操作或 ID 路由。跨库事务依据 [SQLite ATTACH 原子提交条件](https://www.sqlite.org/lang_attach.html)；EXTRA 的目录同步行为见 [SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)。
3. `storage_moves` 先记录待执行目录移动，再重命名目录，最后将所有路径更新与完成标记一起提交。
4. 内容按来源复制后逐表比较完整行集合和数量，保留原 ID、时间、收藏、配对信息。六库绑定同一数据集标识，启动核对结构、外键、目录路由、全局 ID 和计数；缺库、空库、坏库或串库会停止，绝不自动补空库或退回旧库。原文件缺失仅报告、不删除。
5. 内容事务内写入布局版本 3。主库压缩、升级后备份及所有检查完成后才恢复调度与页面；失败或中断仍保持维护封锁。已经完成 v2 的目录不会重搬；显式重试会核对映射并处理后来导入的旧目录。

进程被杀或重启后，状态保留为“需要继续”，页面继续封锁。点击继续会重放未完成的移动：已经重命名但尚未提交路径的目录也可恢复。目标与原目录同时存在时停止，不覆盖任一方；修复冲突后继续。磁盘满、只读、路径越界和目录链接等错误会停止升级并保留错误信息。

升级前后各保留一代数据库备份；服务启动约5分钟后检查备份，之后每24小时运行一次，与采集定时开关独立。旧备份通过完整回读校验才能算作有效代次；最近24小时已有当前版本的有效备份时跳过。至少保留最近3代有效备份，仅清理更早的自动代次，升级前后和手动代次不自动删除。维护页可“立即备份数据库”，并显示最近备份及本次运行中的备份错误。

自动数据库快照**不复制原始媒体，也不是异盘容灾**。如需完整回退，升级前应在停止应用后对整个 `config` 与 `data` 做同一时点备份或 NAS 快照。不能只覆盖旧 `app.db` 或单独替换某个分库。恢复 v3 数据库代次时，停止容器、保留故障现场，在新的 config 中成套放回 manifest 列出的全部6个 `.db` 文件，再用当前版本启动检查；媒体须与该时点兼容。跨媒体目录升级的回退应恢复同一时点的 config 与 data，并运行对应版本。不要删除热回滚日志或迁移状态来强行解封。

下载的 `.part`、Live Photo 改写的原件备份和暂存文件在替换/提交前执行 fsync，替换后同步目录（Linux）。这缩小数据库已记录成功但文件仍未落盘的窗口。SQLite 的保证仍依赖文件系统锁、fsync 和存储设备正确实现；进程强杀测试不能证明 NAS 突然断电、损坏控制器或整盘故障下零丢失，见 [SQLite 硬件假设与故障边界](https://www.sqlite.org/atomiccommit.html)。

## 任务状态与空闲轮询

升级的真实状态来自 `/api/settings/data-upgrade`。v3 的 `status=completed`、`version=3`、`content_shards=true`、`blocked=false` 表示升级完成。阶段、进度、错误和结束状态同步到通用任务面板及事件日志。

健康检查原先每次会重复统计图库索引，并对媒体表分组及站点表关联计数。现已复用同一次请求的索引状态，按数据库内容版本在进程内缓存图库与站点统计。数据版本不变时只读取少量版本号；内容或索引设置改变后重新计算。版本号与统计来自同一只读事务快照，缓存命中不写持久缓存。

旧版 WAL 模式的 `-wal` 和 `-shm` 文件属于数据库运行文件，不能手动删除。v3 打开旧库时由 SQLite 进行恢复及 journal 模式切换；日常使用回滚日志，不再通过保持 WAL 文件打开来优化轮询。目录中额外出现 `-journal` 或 super-journal 本身也不能作为手动清理依据。

## v11.4 缺失原文件检查与修复

旧检查把站点去重时已标为 `duplicate`、原文件已按设计删除的历史路径也统计为缺失。v11.4 检查明确排除这些记录，并单独显示排除数量。旧检查结果会显示“旧规则结果，待重新检查”，不会因升级程序版本就直接把缺失数清零。

维护中的“重新检查并修复缺失”只在用户点击后执行一次：

1. 重新扫描当前引用，排除站点去重记录，将真正缺失、空文件和无效路径写入 `config/data-check-report.json`，提供全部明细及分页查看。
2. 相同路径的图库、站点记录合并处理。图库原文件只从旧平铺目录、数据库目录映射或该内容应属的来源与日期目录中的唯一候选恢复，图片和实况目录分开匹配；其他日期的同名文件、站点标题和 slug 不用于猜测配对。
3. 没有本地原文件时，使用已有站点原文件下载地址，保留原路径与记录 ID。没有下载地址、小红书历史地址或网络失败会列出原因，需要重新同步相应来源。已去重图片不会重新下载。
4. 恢复内容先写独立临时文件，经图片格式或视频流校验并落盘后，通过硬链接原子创建目标；文件系统不支持硬链接时停止该项并报告，绝不退回覆盖已有原文件。已有空文件、目录冲突和多个候选也保留现场。
5. 逐项保存结果，成功和失败都结束本次任务，残留问题可以再次修复；中断后重新检查，只处理仍然缺失的原文件。如果上次在文件落盘后、数据库状态提交前退出，会先校验已恢复文件并补齐状态，不再下载。不会后台循环扫描、下载或删除未恢复的数据库记录。

修复同样使用全页接管并暂停后台写入。检查确认的是引用与文件存在性；网络补下还会校验媒体格式，不保证原站过期、下架或内容变更后仍可恢复同一原始字节。

空闲轮询隔离验证使用 3000 个动态、30000 条图片索引、50000 条媒体记录：两类统计预热后的 50 轮调用耗时约 75 ms，完整健康接口 20 次约 256 ms。连接级 SQL 跟踪未再出现聚合扫描或 DML；两组测试期间进程 `read_bytes` / `write_bytes` 增量均为 0，三个数据库及其 WAL/SHM 的大小和修改时间不变。四个统计读线程与 20 轮媒体、站点写入并行后，缓存结果与直接计数一致。这些结果属于本地 Linux Docker 合成测试，不代表真实 NAS 的磁盘读写情况。
