# Live Photo 配对与历史兼容

B 站动态和小红书笔记新下载的实况，在归档后自动为图片和视频写入相同的永久 ContentIdentifier。图片使用内嵌 XMP，MP4/MOV 使用 QuickTime content.identifier，并保留内嵌 XMP 兼容较旧的元数据工具。配对前后保留文件路径、原扩展名、编码数据及修改时间，现有贴文预览继续按原图库编号工作。

这是针对 Immich 元数据自动配对的兼容格式，不代表 Apple Photos 的完整 Live Photo 捕获格式。Immich 配对还要求图片和视频均被导入同一用户；请先用自己的 Immich 版本做小批导入与播放验证。

## 历史数据

- 启动、普通索引重建、预览和历史配对检查不会补写旧媒体。
- 设置 → 维护与清理 → Live Photo 配对与历史修复：先执行“检查实况配对”，任务在队列完成后按序出现“修复配对”和“修复异常”。三项均进入现有任务队列，支持进度、暂停、取消和失败重试。
- 检查只读取本地文件与元数据，不重新访问来源网站，不改媒体和永久配对记录。
- 左侧 Live Photo 数量统计含实况的动态数；检查报告按图片与视频组统计。“检查实况配对”覆盖全库的 B 站与小红书内容，修复任务结束后的报告只复查上次有问题的内容，标为“局部复查”，不能作为全库配对总数。历史修复报告也会根据保存的范围标识显示此区别。
- “修复配对”只处理一张图与一个实况视频的确定配对，补写标识并保持原路径与编码。“修复异常”先自动尝试补齐原图（原始封面、小红书下载缓存，必要时按来源取回实况自带封面）并在证据确定后确认配对；无法自动判定的缺失图片、多张图片/视频共用一个编号、未被索引的无编号视频会出现在任务报告中，不自动猜测对应关系。
- 旧版无编号媒体需要同名文件，或原始封面与图片像素完全一致作为配对证据；仅由旧索引排序或相似图推断的对应关系保留预览，但不自动写入永久标识。
- `livephoto_pairs` 表保存永久标识，与可重建的 `assets`、`pair_index` 缓存分开。再次执行修复复用标识，已完成文件无需重复写入。
- 写入先在同一文件系统的隐藏临时目录中处理副本，并用不加载项目配置的 ExifTool 回读标识。提交前保存原件备份与恢复日志；提交失败回滚，进程中断则保留备份和日志，下一次显式修复时恢复后重试。取消在组与组之间生效。
- 小红书下载缓存保持原样，归档副本单独配对，并记录配对后的文件校验值供现有“检查本地归档”使用。

## 部署

新镜像包含 Debian `libimage-exiftool-perl`。已有镜像需要重新构建/升级后才具备写入能力，仅替换 Python 文件不够。开发环境需安装 ExifTool，或通过 `APP_EXIFTOOL_BIN` 指定工具路径；工具缺失会明确报错，不会伪报配对完成。

旧目录为 `data/images/<贴文>` 与 `data/livephoto/<贴文>`，数据结构升级后为 `data/<类型>/<来源>/<日期>/<贴文>`，检查与修复统一通过 `folder_locations` 读取实际目录，无需另行同步一份 Live Photo 数据库。提供给 Immich 时需同时覆盖图片与视频，排除 `.thumbs`、`.covers`、`.source_covers`、`.reverse` 和 `.livephoto-*` 临时目录。小红书原始下载缓存也不应重复纳入扫描。尚未手动修复的旧数据继续保持原格式，在 Immich 中可能显示为分开的图片与视频。

## v3 分库后的兼容测试

`docker_app/checks/test_livephoto_immich_shards.py` 使用临时库、本地生成的 PNG/JPEG 图片及真实 MP4 视频，在 B站、站点、小红书三类内容完成实际升级和数据库重开后验证：

- 既有文件全部字节和持久配对标识保持不变，配对记录落入对应物理分库，视频仍可解码且画面数据不变。
- 无项目配置的 ExifTool 能从两份媒体读出相同非空标识；仅数据库标为 `ready` 不算成功。
- 历史缺标识不会因升级或只读检查而被改写；显式修复后可回读且重复修复不再改写。
- 错标识、缺原图、多候选都能报告；替换第二份媒体失败会恢复原件，并可重试成功。
- 不同来源相同组编号使用不同永久标识，新下载配对不会顺带修改未触达的历史组，全库与局部检查范围分别核对。
- 外部导入媒体复用其他分库已有的标识时，显式规范化为新组分配独立标识，原组文件保持不变。

在包含 ExifTool、FFmpeg 和应用依赖的 Linux 环境中执行：
